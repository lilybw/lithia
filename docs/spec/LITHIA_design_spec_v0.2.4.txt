  1. Overview and scope
  LITHIA is a thread-safe, fine-grained reactive engine for Rust on tokio. It brings the core of
  Solid 2.0's signal model to Rust through one primitive, the effect! proc macro.

  Goals

         One primitive for signals, memos and effects.
         Parallel by default: node bodies run on tokio's multi-threaded runtime.
         Explicit dependencies, listed as closure parameters.
         Cycles are allowed, and every cycle lithia can attribute terminates.
         Async only: every node is a stream of values, and a synchronous body is one that
         resolves at once. A pending node never blocks the graph, and values are eventually
         consistent.
         Lifetime by reference counting, with no owner hierarchy.
         Effortless captures: bodies use outer values without manual clones.

  Design Philosophy

         Illusion of Control: Plan for chaos and aim for eventual consistency; control is an
         illusion.
         Usage Limitations: Hard restrictions on API usage are acceptable only where they
         prevent leaks, deadlocks or wrong results, or in favour of separation of concerns, such
         as a read-only view.
         Behavioural Consistency: No special rules or special cases: the same rule holds in
         every context.
         Principles over Performance: Computational overhead is acceptable when it serves
         the principles above; optimisation comes later, within them.
         Loud Failures: A mistake surfaces as a compile error, a panic or a warning, never as
         silent misbehaviour, wherever lithia can detect the mistake; the cases it cannot detect
         are documented where they occur and gathered in section 14.
         Familiar Surface: Recognisable to Solid users, and idiomatic in Rust through
         ownership, RAII and traits.

  3. Public API
  The whole surface is effect! , two node types, two views, the Status , Failure , Site
  and Ghosted types, the Changes stream, typed option constants (3.2), nine free
  functions, the #[lithia::main] and #[lithia::test] attributes, and the test and
   validation modules (13). Four traits state what each handle may do, and NodeValue
  bounds every value (11.1).

  3.1 effect!
  A closure with parameters creates a derived node that depends on them; any other
  expression creates a source node holding that value. Annotations are optional: let count
  = effect!(0); infers SourceNode<i32> .

     let count: SourceNode<u32> = effect!(0);
     // source node
     let guest: SourceNode<User> = effect!(async { fetch_user(7).await }, init =
     User::guest()); // async source node
     let doubled: DerivedNode<u32> = effect!(|count| *count.get() * 2);
     // derived node
     let id: SourceNode<u32> = effect!(7);
     let user: DerivedNode<User> = effect!(async |id| fetch_user(*id.get()).await,
     init = User::guest());              // async derived node
     let log: DerivedNode<()> = effect!(|count| println!("count = {}",
     count.get()));            // effect
     let tick: DerivedNode<u32> = effect!(|count| { for i in 1..=*count.get() {
     yield i; } }); // generator


         Parameters are identifiers naming readable handles in scope: a node or an Accessor .
         Inside the body they refer to the same handles; nothing is shadowed.
         A parameter may carry a type annotation, e.g. |count: SourceNode<i32>| . The
         macro turns it into a type check.
         A source node's value is an ordinary expression evaluated at the call site: a literal, a
         call, a block or a bound name. Normal Rust moves apply, so effect!(my_vec) moves
           my_vec into the node.
         A closure stored as a value is bound to a name or wrapped in parentheses: effect!
         (func) or effect!((|| 0)) . A bare effect!(|| x) is a compile error (4.6).
         An async { … } block creates a source node that stays Pending with its initial value
         until the block produces its first item (section 8).
         A body that contains yield is a generator, written like Rust's gen blocks: each
           yield publishes an item, and the body returns () (3.6). A body without yield
         returns its single item.
         An async { … } block that yields feeds a source node item by item.
           get() returns Arc<K> , so values need no Clone ; numeric use dereferences, e.g.
           *count.get() * 2 .

     /// Read access, required of every dependency; implemented by `SourceNode`,
     `DerivedNode` and `Accessor`.
     /// `fn show(n: &impl Readable<Value = u32>) { println!("{}", n.get()); }`
     pub trait Readable {
         type Value: NodeValue;
         /// Current value. Panics if the node is a ghost under
     `ON_GHOST_CAUSE_FAILURE`.
             fn get(&self) -> Arc<Self::Value>;
             /// Current value, or `Err(Ghosted)` where the node's ghost policy would
     make `get` panic.
         fn try_get(&self) -> Result<Arc<Self::Value>, Ghosted>;
         /// Stream of this node's values from now on; like `tokio::sync::watch`,
     it may skip values.
             fn changes(&self) -> Changes<Self::Value>;
     }


     /// Write access; implemented by `SourceNode` and `Setter`.
     /// `fn reset(n: &impl Writable<Value = u32>) { n.set(0); }`

             type Value: NodeValue;

     ghost.
         fn set(&self, value: Self::Value);
             /// Like `set`, but returns `Err(Ghosted)` instead of panicking.
             fn try_set(&self, value: Self::Value) -> Result<(), Ghosted>;
     }

           Setter has no update or modify . Their closures see the old value, so a holder could
         read it, and the view would no longer be write-only.
           Setter cannot be a dependency. Being notified on every change is itself a way of
         reading the value.
           Setter can reflow . It reveals nothing and acts like a write.
         Only nodes can dispose . Disposal is destructive, so a view must not be able to free
         the node it was handed.
         Views are full references. A view keeps its node alive like any other handle, and is
         cheap to clone.
         No upgrades. A view cannot be turned back into a node or into the other view.
         Enforced by the compiler. Passing a Setter as a dependency, e.g. effect!(|writer|
         …) , fails to compile.

  3.6 Items: yield and changes()
  Every node is a stream of items, and its value is its latest item. A body publishes items
  with yield , exactly as in Rust's gen blocks; ordinary async code observes a node with
   changes() .

     let page: DerivedNode<Fetch> = effect!(async |url| {
         yield Fetch::Loading;                       // published; the run goes on
             let body: Page = fetch(&url.get()).await;
             yield Fetch::Done(body);
     }, init = Fetch::Loading);


     let tick: DerivedNode<u32> = effect!(|count| {
         for i in 1..=*count.get() { yield i; }                  // each item may propagate on
     its own
     });


     let mut updates: Changes<Fetch> = page.changes();
     while let Some(f) = updates.next().await { render(&f); } // may skip values;
     never blocks the graph


         A body that contains yield is a generator. Each yield writes the node's own value,
         visible immediately, and then ends the run's current poll, so an item may get its own
         propagation; items arriving mid-propagation coalesce (7.2).
         A generator body returns () , like a gen block. A body without yield behaves
         exactly as before: its return value is its only item.
         A run that ends without yielding leaves the latest item in place, so a node that has a
         value always keeps one (Case O).
           yield works only directly in the body. Inside a nested closure or async block it is a
         compile error (4.6), which is also how Rust's own generators treat it.
         An existing Stream becomes a node with a short loop in an async source block,
         written with move so the stream is moved in rather than cloned (4.2): effect!(async
         move { while let Some(x) = s.next().await { yield x; } }) .
         Items from a superseded run are discarded by the run counter.
           changes() behaves like tokio::sync::watch : a slow consumer sees the latest value,
         not every value.

  Native generators are on the roadmap: once async gen blocks stabilize, the macro
  lowers generator bodies to them, and user code does not change (16).

  4. Macro expansion
   effect! resolves everything it can at compile time: the dependency list, the captures,
  the site and the initial value. The runtime only receives a ready-made registration.


  4.1 Dependencies
         Each parameter must implement Readable and contributes its node id to the
         subscription list. Mixed value types need no tuple trait.
         An annotated parameter becomes a type check: let _: &SourceNode<i32> =
         &count; .
         Only plain identifiers are accepted. Naming the same node twice, through two
         handles, gives one dependency; repeating a name is a compile error (4.6). A field must
         be bound to a local first.
         A Setter parameter fails to compile, because Setter does not implement
           Readable .


  4.2 Automatic capture
  Rule: a body, or an async source block, captures a clone of everything it references. An
  async source block becomes an async move block that owns its captures, so it never
  borrows from the caller.

         The macro walks the body with a scope-aware syn visitor and collects free
         identifiers: lowercase, in expression position, not bound inside the body.
         For each, it emits let x = x.clone(); inside the expansion block, then a move
         closure. The outer handles stay usable.
         Left alone: uppercase names (constants, statics, types, variants), path segments,
         method and field names, macro names.
         Identifiers in call position, such as max in max(a, b) , are also left alone. Functions
         are items and never need capturing; a local closure called this way is moved instead,
         which fails loudly if it is used afterwards.
           self cannot be rebound with let , so it is captured as __self and the body's self
         tokens are rewritten.
         Formatting macros ( print! , println! , eprint! , eprintln! , format! ,
           format_args! , write! , writeln! , panic! , the assert! family) also get their string
         literals scanned for {name} and {name:…} .




                                                                                            Page 13 of 60
LITHIA design spec v0.2.4




         Nested effect! calls are parsed, not treated as opaque: their parameters and the
         free identifiers of their bodies are captured by the outer body, and a yield inside a
         nested body belongs to the nested node only, so it neither makes the outer body a
         generator nor counts as a nested yield (4.6). Identifiers inside other macro calls are
         captured best-effort.
         Captured values must be Clone + Send + Sync . A non- Clone value is wrapped in
           Arc . Writing move opts out of automatic capture in every form, effect!(move |a|
         …) , effect!(async move |a| …) and effect!(async move { … }) : the body is
         used as written. A closure body must then meet the bounds in 11.1 itself, typically by
         cloning inside; an async source block runs once, so it needs only Send + 'static and
         can own a stream that is neither Clone nor Sync .
         A wrong guess is usually caught: a missed identifier is moved, so later outer use fails
         to compile, and a wrongly captured one is cloned or fails to compile. A clone can still
         change behaviour unnoticed; a cloned mpsc::Sender , for example, keeps its channel
         open. Such values belong outside the body, or inside one written with move .
         Clones happen once, when the node is created, and live together in one
         Arc<Captures> . Each run of an async body clones that Arc (one atomic increment),
         so the run's future owns what it uses and can be spawned.

  Forward compatibility. Rust's planned Share trait and move(expr) captures fit the
  capture rule above without changing consumer code (16).

  4.4 Initial value
         Source nodes start with their value.
         Derived nodes and async source nodes start with init if given, otherwise
           K::default() . A body that returns nothing has K = () .

           init is required only when K has no Default ; leaving it out then is a compile error
         (4.6).

  6. Writes and batching
  A write is visible to every read immediately; only the reruns it causes wait for a batch
  boundary. The rule is the same in ordinary code and inside bodies.


  6.1 Writes
           set , update and modify take the node's write lock, store the new value and record
         the node as changed in the current batch. A write to a source node is a run whose only
         item is the new value, so it supersedes, and is superseded, like any other run (7.3).
          yield does the same for a derived node's own value (3.6), but never makes the node
         a writer (7.4).
           update(|old: &K| -> K) runs its closure synchronously on the caller's thread, so
         the closure needs neither 'static nor move .



                                                                                                           Page 18 of 60
LITHIA design spec v0.2.4




           modify(|v: &mut K|) does the same through a mutable reference: it clones the
         current value, runs the closure on the copy and publishes the copy. Reads are lock-
         free and may begin at any moment, so the copy cannot be skipped; for large values a
         persistent collection (such as the im crate) makes it cheap.
         Any lithia write inside an update or modify closure, or inside an equals comparator,
         panics, through a thread-local flag, and so do lithia::reflow and
           lithia::dispose . Otherwise two threads updating A and B in opposite nesting order
         would deadlock on each other's locks. Reading nodes and creating nodes are allowed
         there.
         Only modify requires K: Clone , and only where it is called. update builds the new
         value from a reference to the old one, which readers may still hold.
         Values are replaced, never mutated where readers can see them. Interior mutability
         inside a value (a Mutex or atomic field) compiles, but bypasses lithia: such changes
         trigger no reflow.
         By default every write propagates; the equals option lets a node skip equal values
         (6.4).
         Creating a node and calling lithia::reflow are recorded in the batch the same way.
         A node links to its parents the moment it is created (11.4); only its scheduling waits for
         the batch.


  6.2 Batch boundaries
     1. The end of a poll. In tasks started by lithia::spawn , #[lithia::main] or #
         [lithia::test] , everything done during one poll forms a batch, delivered when the
         poll returns. In practice, a batch is everything between two .await s that suspend.
     2. Bodies. Bodies run as lithia tasks, so the same rule applies. A body is polled until it
        suspends at an .await or a yield , and each suspension delivers a batch. A run's
        first poll therefore delivers into the epoch that started the run, and every later poll
        opens child epochs (7.1). The batch is delivered after the poll returns, including when
        the poll wrapper caught a panic (9.1), so a body that panics still propagates the writes
         it made.
     3. lithia::flush() . Delivers the current batch at once; inside a body, as one child
         epoch per epoch the run serves (11.3).

  Tasks that lithia did not start, such as a plain tokio::spawn or a #[tokio::main] entry
  task, have no poll boundary lithia can see. There, each write forms its own batch: still
  correct, just less batched. A node creation made inside an update or modify closure or



                                                                                             Page 19 of 60
LITHIA design spec v0.2.4




  an equals comparator is delivered when the closure returns, never while the write lock is
  held. Guarantees that rely on one batch, such as the single run in Case A, then need
  lithia::spawn or the lithia attributes. Writes made this way from inside a body also
  carry no writer set (7.4).


  6.3 Explicit postponement
   lithia::defer(f) runs f once the current batch's epoch has settled. Child epochs
  started by later polls are not waited for, so it never waits on async work. It needs no
  engine support of its own: it is a thin helper over the epoch tree (7.1). f runs as a lithia
  task on the caller's runtime and starts a fresh epoch with an empty writer set (7.4), so it is
  also the way to feed a value back into a cycle on purpose; a loop through it is unattributed
  and triggers the rerun-rate warning (12). In a task lithia did not start, each write is its own
  batch, so defer fires after the propagation of the most recent write. Use it when a write
  must deliberately happen after the current propagation, instead of being visible to it.


  6.4 Equality ( equals )
  By default every write propagates. The equals option lets each node decide which new
  values count as changes:

     let name: SourceNode<String> = effect!(String::new(), equals = lithia::eq);
     let user: SourceNode<User> = effect!(User::guest(),
             equals = |a: &User, b: &User| a.id == b.id && a.version == b.version);


           equals takes |old: &K, new: &K| -> bool , where true means equal.
           lithia::eq is a ready-made comparator for K: PartialEq that requires the trait
         only where it is used.
         When a new value equals the current one, three things happen: the node keeps its old
         value, changes() skips the new one, and nothing propagates. This holds for set ,
          update and modify on source nodes, and for yielded items and return values on
         derived nodes. Because an equal value is discarded, a comparator that tolerates small
         differences (an epsilon) also swallows a series of small changes for good; compare
         identities or versions instead. An equal write is no run, so it does not supersede an
         async block or generator feeding the node. If the comparator panics, a write panics in
         its caller and leaves the value unchanged, and an item from a run fails that run (9.1).
           flags = ALWAYS_PROPAGATE keeps the first two and propagates anyway, for nodes
         that want deduplicated storage but every trigger.




                                                                                            Page 20 of 60
LITHIA design spec v0.2.4




         There is no implicit default. A node never compares unless asked, so an effect's ()
         values keep propagating, and deriving PartialEq on a type changes nothing by itself.
         With equals , most write cycles converge on their own; the writer-only cut (7.4)
         remains the backstop.


  7. Propagation
  lithia propagates each batch through the graph: every affected node waits until its
  affected parents have settled, then runs only if one of them changed. Diamonds therefore
  run once with consistent inputs, equal values stop propagating, and a write cycle stops at
  the first writer that would run twice on one chain.


  7.1 Seeds and epochs
  A batch seeds an epoch with:

         written source nodes, which propagate to their subscribers;
         new derived nodes and new async source nodes, which get their first run;
           lithia::reflow targets, which take a new version at once and run again (7.2).

  A node seeded several ways runs once.

  Epochs form a tree. An outside batch starts a root epoch. A run's first poll delivers into
  the epochs that started it, and every other delivery from the run opens one child epoch
  per epoch the run serves: a later poll, a flush() inside its body, or a
   lithia::spawn_blocking from its body completing while the run is in flight. An epoch
  settles when it has no open entries left (7.2). flush waits for the caller's subtree to settle
  (11.3), defer for its own epoch alone (6.3), and lithia::test::settled until every run
  started in a node's subtree has ended (11.3).

  A run is in flight from the moment it starts until it ends or is superseded. While in flight it
  is either active, meaning it is being polled or lithia has rescheduled it after a yield , or
  suspended, meaning it is pending for any other reason, including awaiting another node's
   changes() . A run releases its children at its first yield or suspension, whichever comes
  first (7.3), and closes its entries once it has ended or is suspended.


  7.2 Scheduling
  Dependencies must exist before the node that uses them, so the dependency graph is
  acyclic and NodeId order is a topological order. Every cycle is a write cycle, handled in 7.4.



                                                                                            Page 21 of 60
LITHIA design spec v0.2.4




  Each node has a phase word, which says among other things whether a run is in flight (a
  node counts as queued when one is and another entry is already runnable), and a version:
  the stamp, from one process-wide clock (11.4), of its last changed item (any item under
   ALWAYS_PROPAGATE ) or of its last lithia::reflow , taken when reflow is called. equals
  therefore decides what counts as a change (6.4). A node also holds one entry per epoch it
  is framed in, open from the moment framing reaches it until it settles that epoch.

         Framing. When a node changes, each subscriber opens an entry for that epoch that
         waits on it, and so on downstream, so a diamond's join waits for both paths. Every
         release names the epochs it serves and, per epoch, carries the parent's version if it
         changed.
         Running. When an entry's waiting set empties, the node becomes runnable for that
         epoch if a release in it carried a change stamped later than the start of the node's last
         run; anything stamped earlier was already visible to that run (11.4, step 5). A new node
         has no last run, so its first run always happens. All entries runnable at once coalesce
         into one run, which takes over their entries (7.3). Every release first applies the writer
         check (7.4): a node that already wrote on the chain in that epoch is not released to run
         (Case P).
         Settling unchanged is the only other way an entry closes: the node closes it and
         releases its subscribers for that epoch, with its own version unchanged. It happens in
         three situations:
                 no release in the entry carried a newer change, so equal values and runs that
                 produced nothing stop there (Case R);
                 the writer check refuses the node (Case T). This records nothing, so a later real
                 change still runs it, while a batch that merely frames it never does;
                 the node can no longer run, because it was freed or disposed, its weak reference
                 cannot be upgraded at release, or its runtime has shut down, including when its
                 run is aborted for one of these reasons.
         During a run. Framing never disturbs a run in flight: a later epoch simply opens its own
         entry. Only when an entry becomes runnable while a run is in flight is that run
         superseded (7.3, item 4), and the new run serves the runnable entries together with
         the old run's, so a restart never reads a half-propagated join. This holds whichever
         epoch the entry belongs to.
         Fragility. A parent entering Failed fails each fragile child whose condition now holds,
         without running it. A parent leaving Failed reruns each fragile child whose condition
         no longer holds, whatever the versions say (9.2).




                                                                                               Page 22 of 60
LITHIA design spec v0.2.4




           lithia::reflow raises the node's version when it is called and starts one more run
         after any run in flight, without superseding it, for source and derived nodes alike. The
         node's children rerun even when equals judges the new item equal.
         Ties are broken in NodeId order.


  7.3 Runs and items
     1. A node released to run (7.2) starts a run on the runtime where it was created (11.3),
        taking over the open entries of the epochs it serves and recording those epochs as
        the ones it serves (5). Every run is a stream of items: a body without yield produces
         its return value; a generator produces one item per yield , and each yield also ends
         the run's current poll (3.6). An async body may also suspend at any .await .
     2. Items produced before a run's first yield or suspension belong to the epochs it serves.
        At that moment the worker running it frames the downstream region of its writes (7.4,
        11.4) and releases every node waiting on it. A changed item raised the node's version;
        a run that produced nothing, or only values equals judged equal, leaves the version
        unchanged, so its children see no change. The run closes its entries once it has ended
        or is suspended (7.1), and keeps their writer sets until it ends (7.4).
     3. Items produced later arrive in a later delivery, which opens child epochs (7.1).
     4. Supersession. When a new run of a node is due while one is in flight, because an entry
        became runnable (7.2) or a source node was written (item 5), the old run is
        superseded: an async run is aborted, a synchronous one is left to return and its result
        is discarded, and items from the old run are discarded by the run counter. Writes the
        old run already delivered stay applied, as after a panic (9.1), and a run counts as
        synchronous until it first suspends. An abort takes effect only when the old run's
        current poll returns, so the new run starts after that, and every yield checks the run
         counter under the write lock, so a superseded run can never publish an item. Other
         sections refer to this rule rather than restating it.
     5. A write to a source node is a run that produces the written value as its only item and
        finishes at once; an equal write is no run at all (6.4). An async block or generator
        feeding a source node is a run like any other, so a later write supersedes it by item 4
        (section 8).


  7.4 Writes during propagation
  Every run carries a writer set: the nodes that wrote to another node, or called reflow on
  the causal chains that led to it. Producing its own items never makes a node a writer. A
  write from body W to a source node T is always applied, and T's subscribers are routed

LITHIA design spec v0.2.4




  against C, that writer set plus W itself:




  write routing at every step · 2 decisions, 4 outcomes

  Only nodes that already wrote on the chain are skipped. A pure node inside a loop reruns
  and ends up consistent (Case M), and so does a sibling outside it (Case H). The same
  check applies at every later step, not just to T's direct subscribers, so an unconditional
  write-back through a memo stops too (Case P).

         A subscriber of T sees T's new version (7.2) and carries C into its run, including when
         it runs again after finishing.
         Creating a node is not a write, but it continues the chain: a new node's first run carries
         its creator's writer set, without the creator. A loop that returns through node creation,
         as in Case S, is therefore unattributed: it keeps running and triggers the rerun-rate
         warning (12). Leaving the creator out is deliberate, so that a child can feed its creator,
         as a loader filling a cache its creator renders does (Case U).
         Writer sets accumulate per node within one epoch, in the node's entry for it (7.2), and
         close with the entry. Within an epoch a node's set only grows, as the union of every
         set that reaches it in that epoch. Meshes such as n-way bindings therefore cost about




                                                                                             Page 24 of 60
LITHIA design spec v0.2.4




         n² runs instead of one per path, and a writer from an earlier item is never cut on a later
         one (Case Q).
         A run serving several epochs keeps each entry's writer set apart: its writes are routed
         once per epoch, and a subscriber is cut only in the epochs where it already wrote.
         A run keeps its entries' writer sets until it ends, even after closing the entries, and
         each child epoch it opens inherits the writer set of the epoch it descends from.
         Epochs therefore stay a tree, and loops through async nodes terminate.
           lithia::reflow(&node) counts as a write: called from the node's own body, the
         node itself is in C and does not rerun, but its children do.
         Writer sets follow a run's own work, meaning its deliveries (7.1). Detached work starts
         fresh: lithia::spawn , lithia::defer , Drop code that lithia runs (10.3), a plain
           tokio::spawn , a thread or a channel all deliver outside batches with an empty writer
         set, so a loop through them is unattributed. So does a lithia::spawn_blocking that
         completes after its run has ended or been superseded; blocking work cannot be
         aborted.
         Every cycle passes through a write, and each writer appears at most once per chain
         within an epoch, so attributed loops terminate. Unattributed loops may run
         indefinitely; a node rerunning faster than a configurable rate gets a warning (12),
         never a failure.
         A cut writer keeps the result of its last run until a later epoch changes one of its
         parents, since a change from another chain in the same epoch is refused too: a
         memo's value, or an effect's side effects, may reflect inputs from before the cut. In a
         cycle with several writers, which one is cut depends on scheduling, and so may the
         cycle's final values (7.5). Cuts are logged (12): at warn when the writer holds a value,
         at trace for an effect.
         With equals (6.4), most loops converge before the cut is needed.


  7.5 Determinism
  Scheduling ties are broken in NodeId order, which is topological. Whether a write joins,
  restarts or reruns a subscriber depends on timing, and so does the NodeId order of top-
  level nodes created from several tasks. Concurrent runs may also observe each other's
  writes. Which writer a cycle cuts, and so a cycle's final values, may depend on timing too
  (7.4). All of this is accepted.

  8. Pending, async and generators
  Every run is asynchronous in principle; a synchronous body is simply one that resolves at
  once. A pending node never blocks the graph: it keeps its latest item, its children run on
  that item, and its next item starts a child epoch (7.1).

         A node is Pending from the start of a run until the run produces an item or ends.
         Readers and children keep using the latest item meanwhile.
         A run releases its children at its first yield or suspension, so they run optimistically on
         the latest item (7.1, 7.3).
         A write cycle stops at the first writer that would run twice on one chain. An async
         node that does not write is not a writer, so it reruns once and its value catches up.
         Supersession: works as in 7.3, item 4.

  Async source nodes ( effect!(async { … }) )

         An async block or generator is the source node's first run (3.6). The run is registered
         when the node is created, so the node is Pending from that moment, with init or
         K::default() , until the run produces an item; a panic marks it Failed .
         Every write starts a new run (7.3, item 5), so a write supersedes the block by the
         ordinary rule, even before the block has started: the block is aborted, or never starts,
         and any late items are discarded (Case G). A single write therefore stops a source fed
         by a stream for good.
         The block gets the same automatic capture as closure bodies (4.2), and its task holds
         the node only weakly, like every run (10.1).
           reflow on a source node re-emits its current value and raises its version, so its
         children rerun. Unlike a write, it does not supersede an async block or generator that
         is still running.
         Because a write is just a run, writable derived nodes (Solid's writable memos) would
         need no new machinery; they remain out of scope for v0 and are on the roadmap (16).

  Generators

         A body or async source block that contains yield is a generator (3.6). Each yield
         publishes an item and ends the run's current poll, so an item may get its own
         propagation; items arriving mid-propagation coalesce.
         The node is Pending until the first item and Ready from then on, even while the run
         continues: Status describes the current value, not whether work is in flight. When
         the generator ends, the latest item stays; a panic marks it Failed .




                                                                                               Page 26 of 60
LITHIA design spec v0.2.4




         On a derived node, a rerun drops the current generator and starts a new one. On a
         source node, a write starts a new run, which supersedes it.
           flush() waits through a generator's yield s but not past any other pending poll, so
         an async generator may still be running when it returns, and a synchronous generator
         that never ends keeps it waiting. lithia::test::settled waits until it ends, so an
         endless generator needs a timeout in tests.
         A Stream returned without yield is an ordinary value; most streams are not Sync ,
         so storing one needs a wrapper such as Mutex<Option<S>> .

  Eventual consistency

         Once outside changes stop and every run has ended or suspended for good, every
         value matches what its body computes from its inputs, except a writer whose re-
         trigger a cycle cut (7.4), and a failed node, which keeps its last successful value, with
         its fragile children (9).
         Within one propagation, synchronous diamonds stay glitch-free (Case B), as long as
         no concurrent epoch writes the same sources (7.5, 11.4). Writes guarantee only final
         values: a sibling may briefly see a value before a clamp lands (Case H).
         Between propagations, a child can combine a fresh item from one parent with an
         older one from another, and nodes downstream of later items run again.
         Intermediate items may be skipped: children and changes() see the latest item, not
         necessarily every item.
         Repetition such as polling cannot be expressed as a cycle in the graph; write it as an
         async source block that loops, awaiting a timer and yielding each result (3.6), or drive
         it from outside.


  9. Failure
  A panicking body puts its node into Failed , which behaves like Pending : the node keeps
  its last successful value, children keep running on it, and its next run takes it back to
  Pending until that run produces an item or fails again (5.3).


  9.1 Panics
         Every run is polled through a wrapper that catches panics ( catch_unwind ). The
         wrapper catches the panic and marks the node Failed.
         A warning is emitted through tracing , with the site and the panic message.




                                                                                              Page 27 of 60
LITHIA design spec v0.2.4




         A failed node reruns when a dependency changes or on lithia::reflow . A new run
         clears the failure: the node is Pending until the run produces an item, and its children
         rerun only if that item changed (7.2).
         No rollback. Writes the body made before panicking stay applied and still propagate,
         because the batch is delivered after the panic is caught (6.2). Nodes it created follow
         the normal lifetime rules.
         Panics inside update or modify happen on the caller's thread and propagate to the
         caller. The value is unchanged: update only reads the old value, and modify works on
         a copy that is discarded. Inside a body, the panic fails that body's node as usual. The
         write lock does not poison itself (for example parking_lot ).
         Builds with panic = "abort" cannot catch panics; the process aborts.


  9.2 Fragility
  By default, a child does not fail when a parent fails: it keeps running on the parent's last
  successful value. The fragility option makes it fail instead:


     Value                  The child fails when

     not set (default)      never because of a parent

      FRAGILE               any parent is failed

      SEMI_FRAGILE          all parents are failed


         A child failing due to fragility does not run its body. Its Failure names each failed
         parent's failure in its causes .
         A parent entering Failed fails its fragile children whose condition now holds, without
         running them; a parent leaving it reruns those whose condition no longer holds,
         whatever the versions say (7.2). Its other children rerun only if the recovered item
         changed.
         A pending parent does not count as failed. A ghost parent under
           ON_GHOST_CAUSE_FAILURE does. A child failed by fragility gets the message "parent
         failed", with its failed parents' failures as causes; a ghost parent contributes a failure
         with the message "parent disposed" and its own site. A node whose runtime has shut
         down gets "runtime shut down".
         The values are mutually exclusive, so fragility is a named option like ghost . The
         names are provisional.

  10. Lifetime and disposal
  A node lives while something holds it: a handle, or a child that depends on it. There is no
  owner hierarchy, and nothing keeps a node alive on its behalf.


  10.1 Reference counting
  Strong references

         Every handle held anywhere, node or view: locals, collections, captures, other nodes'
         values.
         A child's dependency on each of its parents.

  Weak references

         A parent's list of subscribers.
         Scheduled, queued and running runs, which hold their node weakly, so an unused
         node can be freed before its first run.

  Consequences

         Dependencies exist before the node that uses them, and captured handles exist
         before the body that captures them, so dependency and capture edges always point
         at older nodes. Handles held in values can point anywhere, so the only possible cycles
         run through values, for example a source node whose value holds a handle to one of
         its own subscribers. Such leaks are silent; tests can catch them by checking
           lithia::test::live_nodes() .
         Freeing runs bottom-up: a node is freed when its last strong reference goes, which
         may in turn free its parents. Strong references are plain Arc s and weak ones Weak s,
         so the count is Arc 's own. A node's Drop moves its parents onto a worklist instead of
         dropping them recursively, so dropping the end of a long chain cannot overflow the
         stack. A freed node also removes itself from each parent's subscriber list, so creating
         nodes on every run does not grow those lists. lithia::dispose still frees top-down
         (10.4).
         A derived node stops when its last handle drops, even while its parents live.
           DerivedNode is #[must_use] ; because let _ = silences that lint, a node freed
         before its first run finishes also triggers a warning (12).
         A node created in a body is freed when the body ends, unless a handle escapes: into a
         collection, another node's value or a return value. Nothing accumulates across reruns
         unless a handle is kept (10.2).

         A function can return a derived node: the node keeps its parents alive (Case I).


  10.2 Keeping effects alive
  An effect runs for exactly as long as something holds its handle. Three patterns cover the
  common cases:

     let count: SourceNode<u32> = effect!(0);
     let _log: DerivedNode<()> = effect!(|count| println!("{}", count.get())); //
     for the life of this scope

     let rows: SourceNode<Vec<SourceNode<String>>> = effect!(Vec::new());
     let printers: DerivedNode<Vec<DerivedNode<()>>> = effect!(|rows| {
         rows.get().iter().map(|row: &SourceNode<String>| {
             let row: SourceNode<String> = row.clone();
             effect!(|row| println!("{}", row.get())) // for the life of this
     run's value
             }).collect()
     });


         For the life of a scope: bind the handle. The effect stops when the binding goes out of
         scope; let _ = effect!(…) drops it at once, and the warning in section 12 catches
         that.
         For the life of a value: return the effects as part of a derived node's value. When the
         next run replaces that value and nothing else holds the old one, the old effects are
         dropped and stop. This is how nested, per-item effects are written, and it needs no
         special rule: it is ordinary RAII on the node's value (10.3).
         Indefinitely: store the handle where its owner lives: a struct field, a collection,
         another node's value or a static .

  Overlapping generations. The old effects live exactly as long as the old value does, by the
  ordinary rule that a node lives while something holds it. The value's pending drop (10.3)
  holds it until that drop has run, which may be after the propagation that replaced it, and
  so does a reader that kept the replaced value, such as a changes() consumer holding an
  item across an .await . Until then the old and new effects both react, which can duplicate
  side effects. Children that depend on the node never cause this, because a change
  restarts them.

  10.3 RAII cleanup
         When a new item replaces a node's value, the previous value is dropped. When a node
         is freed, its value and body are dropped.
         Drops never run inside the scheduling protocol (11.4). Replaced values, values
         discarded by equals or by a superseded run, and the values and bodies of freed or
         disposed nodes, are dropped on the node's runtime, through spawn_blocking under
           catch_unwind , so a Drop may spawn tasks, block or write nodes. Its writes are
         detached work: an outside batch with an empty writer set (7.4).
         If the node's runtime has shut down, tokio would drop the payload on the spawning
         thread, which may be a worker in the middle of scheduling. Such drops go to a lithia-
         owned drop thread instead, also under catch_unwind .
         An old value is dropped only after the node's write lock is released, so a Drop that
         writes nodes cannot deadlock.
         If a reader still holds the previous Arc<K> , the drop happens on that reader's thread
         when it lets go. Drop cannot be async, so graceful async cleanup spawns a task.


  10.4 Manual disposal
   lithia::dispose(&node) frees the node and every descendant that has no live parent
  outside the freed branch, regardless of outstanding handles. Disposing twice does
  nothing. The API docs carry a use-after-free warning.

  11. Concurrency and runtime
  LITHIA runs on tokio's multi-threaded runtime: values live in per-node lock-free cells, and
  scheduling is a protocol on per-node state, with no central thread (11.4).

         Reads: get() loads the node's ArcSwap<K> without locking, from any thread.
         Writes: applied on the caller's thread under the node's write lock, then recorded in
         the caller's batch.
         No coordinator: whichever worker finishes a run or delivers a batch carries out the
         scheduling, under per-node locks (11.4). There is no central thread to bottleneck on,
         and none that user code must be kept away from.
         Bodies: every run is spawned on the tokio runtime where its node was created. Long
         synchronous work inside a body blocks a worker thread and belongs in
           lithia::spawn_blocking , whose writes stay part of the run (7.1).
         One run per node: at most one run of a node is in flight; supersession follows 7.3, item
         4.

  11.3 Scopes
         There is no graph object and no central scheduler: nodes link to each other directly, so
         nodes created anywhere can depend on each other without any declaration.
         A task started by #[lithia::main] , #[lithia::test] or lithia::spawn , including
         one spawned from a body, roots a scope: the subtree of epochs its batches start (7.1).
         Any other task, or a thread outside any task, acts as its own scope: the epochs its
         writes start, one batch per write (6.2).
         Bodies need no scope of their own, since their polls already sit in the tree.
         A write from one part of the program into another stays in the writer's subtree,
         because the epoch it lands in is the writer's epoch or a child of it.
           flush() returns once every run in the caller's scope has finished or suspended.
         Called from a body, it delivers the body's pending batch as one child epoch per epoch
         the run serves and waits for those subtrees, which is exactly what the body has
         caused so far. It never waits for async results, and it ignores runs suspended in
         flush() themselves, so two bodies flushing at once cannot deadlock.
           lithia::test::settled(&node) delivers the pending batch, then waits until every
         run started in the node's subtree has ended. It may wait forever on an endless run,
         and is exempt from stability guarantees.
         Bodies are spawned on the runtime where their node was created. A run whose
         runtime has shut down marks its node Failed .
         Creating a derived node or an async source block with no runtime at all panics, as
         tokio::spawn itself would.


  11.4 Scheduling protocol
  lithia's scheduler is derived from MV-RP, the thread-safe propagation algorithm of
  REScala (Drechsler, Mogk, Salvaneschi and Mezini, OOPSLA 2018). It keeps MV-RP's
  framing phase, exclusive runs per node and pipelining. It leaves out what MV-RP uses to
  make concurrent updates strictly serializable: per-node version histories, a serialization
  graph and retroactive repair. lithia promises only eventual consistency between
  concurrent epochs (8), so it needs none of these, and its bodies write to arbitrary nodes
  mid-propagation, which MV-RP's up-front framing could not predict anyway.

     1. One short scheduling lock per node guards its entries (waiting set, writer set and
         newest change per epoch), the epochs its in-flight run serves, the stamp of its last
         run, and its subscriber list. Its version and phase are atomics, so others read them
         without a second lock. A thread holds at most one scheduling lock at a time, except



                                                                                             Page 34 of 60
LITHIA design spec v0.2.4




         while creating a node (step 7), and never runs user code while holding one. A write
         lock may already be held when a scheduling lock is taken, but no thread takes a write
         lock while holding a scheduling lock. The protocol itself never takes write locks, so
         this single order rules out deadlock. Values stay lock-free to read.
     2. Framing. The thread that delivers a batch frames its whole downstream region,
        opening an entry on every reachable node (7.2), before it releases any run, so a join
         never runs before its second path reaches it. A body's writes are framed when its poll
         delivers them, before its own subscribers are released. Framing is a graph walk with
         no user code in it.
     3. Pipelining. Entries are per epoch (7.2), so a later epoch can run a node as soon as an
        earlier run of it finishes, even while the earlier epoch is still busy further downstream.
         A release for one epoch never touches another's entry, one scope's flush never
         waits on another scope's traffic through a shared node, and parents in different
         epochs cannot starve a join. This protects synchronous nodes; an async node can still
         be aborted indefinitely when input arrives faster than it finishes.
     4. Release. The worker that finishes a run updates each child under that child's lock
        (7.2). If the release makes exactly one child ready and that child belongs to the
         worker's own runtime, the worker may run it inline, which is the fast path (11.2);
         otherwise it hands every ready child to the child's runtime. A task spawned from a
         worker waits in that worker's LIFO slot, which other workers cannot steal from, so
         running a body inline after spawning siblings would hold the last one up until the body
         ends. Inline execution is a loop, never recursion, so a long chain cannot overflow the
         stack. Strong references the protocol takes from weak subscriber lists are dropped
         only after the lock is released, so a node's teardown never runs inside the protocol.
     5. Clock. Versions and run stamps come from one AtomicU64 . A node publishes its new
         value first and then takes its stamp with a fetch_add ; a run reads the clock for its
           ran_at before its body's first read. Both use SeqCst in v0, so a stamp at or below
           ran_at belongs to a value published before the run read anything, and a node is
         runnable only for a stamp strictly greater than ran_at (7.2).
     6. Epoch accounting. Each epoch counts its open entries atomically, whether a node or
         the run serving it holds them, and links to its parent epoch. A run opens its children's
         entries before it closes its own, so the count never reaches zero while work remains,
         and always reaches it once work stops (7.2). This is a single-process form of the
         progress tracking in timely dataflow.




                                                                                             Page 35 of 60
LITHIA design spec v0.2.4




     7. Creation mid-propagation. A new node holds its own lock while it takes each parent's
         lock in turn. For every epoch a parent has an open entry in, or its in-flight run serves
         (5), the new node opens an entry that waits on that parent. It also opens an entry for
         its own seed epoch, and reads every other parent's settled value (Case N). This is
         deadlock-free: a thread that reaches the new node through a parent it has already
         linked to holds no scheduling lock at that moment, and the protocol never holds a
         parent's lock while taking a child's.
     8. Verification. The protocol is model-checked with loom over the validation cases,
         including every way a framed node can leave without running and the clock rules in
         step 5, and specified in TLA+, before it ships.

  Unlike in MV-RP, concurrent outside batches are not ordered as if they ran one after
  another: a join may combine changes from two epochs. Within one epoch, everything in
  section 7 holds unchanged. MV-RP measured 20–25% single-threaded overhead for its
  full machinery (section 5.2 of the paper); lithia's subset should cost less, which remains to
  be measured (15).

         Native generators. yield in effect! uses the syntax of Rust's unstable gen and
           async gen blocks. Today the macro rewrites each yield into a write and the end of a
         poll, as the async-stream crate does on stable. Once they stabilize, the macro lowers
         generator bodies to native async gen blocks. Like today's lowering, they allow a
         borrow to be held across a yield , which plain gen blocks do not, so user code does
         not change. async gen is further from stabilization than gen (3.6).
           Share and precise captures. Rust's 2026 project goal for ergonomic ref-counting
         prototypes a Share trait plus move(expr) closure captures (goal). Handles will
         implement Share once it stabilizes, and captures of Share types will use it. The
         capture rule stays the same, so consumer code does not change (4.2).
         Writable derived nodes. Because a write is just a run, Solid-style writable memos
         need no new machinery; they are out of scope for v0 (1, 8).
         Flags for pending parents and mixed reads. Waiting on pending parents and avoiding
         mixed reads return as flags once they are designed; the earlier
           DELAY_ON_PENDING_PARENT and AVOID_MIXED_READS drafts were dropped until then
         (3.2, 14).
         Devtools, out of scope for v0 (12).
         Performance work, guided by the benchmarks in section 15, once the semantics are
         settled (11.2).
